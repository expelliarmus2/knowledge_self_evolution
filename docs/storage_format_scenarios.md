# 场景文档 B：用"数据库系统四层次"理解两种存储选型

> 框架：**查询语言 → 逻辑数据模型 → 物理执行引擎 → 物理存储结构**（数据库系统经典分层）。
> 结论先行：**没有最好的存储格式，只有与"问题形态"最匹配的存储格式**——知识库多跳问答匹配图存储，科研入组筛查匹配关系存储；统一门面让两者共存，而不是互相替代。

---

## 1. 四层次框架

一个数据系统从用户到磁盘可以切成四层，每层回答一个问题：

| 层次 | 回答的问题 | 举例 |
|---|---|---|
| ① 查询语言 | 用户**怎么表达**要什么 | SQL / Cypher / Gremlin / 条件 IR / 自然语言 |
| ② 逻辑数据模型 | 数据**怎么组织**才贴合问题 | 关系（表） / 属性图（节点-边） / 文档 / 键值 |
| ③ 物理执行引擎 | 查询**怎么算**（算子、计划、索引扫描） | 关系代数算子 / 图遍历算子 / ANN 检索 |
| ④ 物理存储结构 | 数据**怎么落盘** | B+Tree 行存 / 列存 / 邻接表 / CSR / HNSW |

**选型逻辑**是自上而下的：先看问题（查询形态）→ 定逻辑模型 → 再选引擎 → 最后决定落盘格式。
如果先定存储再套问题，就会像"用图存所有东西"或"把一切塞进一张大表"一样别扭。

---

## 2. 两个场景在四层上的对照

### 场景一：知识库多跳问答（ChunkHop）

| 层次 | 本场景的实现 | 说明 |
|---|---|---|
| ① 查询语言 | **自然语言**（"星辰科技的创始人是谁？"） | 用户不写查询语言，由 embedding + 图谱遍历代为翻译 |
| ② 逻辑数据模型 | **属性图**：`实体(节点) -关系(边)-> 实体`，边上挂 chunk 证据 | 问题本质是"沿关系链跳转"，图模型让跳转是一等公民 |
| ③ 物理执行引擎 | NetworkX 图算子（BFS/多跳扩展）+ FAISS ANN + personalized PageRank | 向量做语义粗筛，图算子做结构扩展，PPR 做全局排序 |
| ④ 物理存储结构 | `graph.pkl`（内存邻接表）+ FAISS 三索引文件 + PPR 缓存 | 图常驻内存遍历；向量用近似最近邻索引 |

### 场景二：科研入组筛查（cohort demo）

| 层次 | 本场景的实现 | 说明 |
|---|---|---|
| ① 查询语言 | **结构化条件 IR**（JSON：age / diagnosis / lab / event / medication） | 每个条件都可编译、可审计；最终落成 SQL 语义 |
| ② 逻辑数据模型 | **关系**：5 张表（patients / diagnoses / labs / medications / events） | 判定是"属性过滤 + 表间 EXISTS 关联"，正是关系代数的集合语义 |
| ③ 物理执行引擎 | SQLite 查询计划器：B+Tree 索引 + EXISTS 子查询 + 三值 CASE | include 求交、exclude 求否，一次 SELECT 扫完全部患者 |
| ④ 物理存储结构 | **SQLite 单文件**（B+Tree 行存，外键引用完整性） | 单文件可交付、可审计、零依赖 |

## 3. 存储格式详解：四种物理结构

### 3.1 行存（Row-store，SQLite/PostgreSQL/MySQL 默认）

一行的所有字段**连续存放**，读一行一次 I/O：

```text
磁盘页（page）布局：
┌─────────────────────────────────────────────────┐
│ patient_id | name      | birth_date | sex       │
│ 1          | P001-合格 | 1970-05-01 | M         │  ← 一次 I/O 拿到整行
│ 2          | P002-年龄 | 1940-01-01 | M         │
│ 5          | P005-缺检 | 1968-09-09 | F         │
└─────────────────────────────────────────────────┘
```

适合：**点查**（按主键取整行）、**整行读**（给患者下结论要读他全部属性）。
入组筛查正是"逐患者整行 + 子表 EXISTS"——行存 + B+Tree 主键索引命中它的工作负载。
SQLite 全库就是**一个文件**，页内行 + 页间 B+Tree 指针：

```text
demo.db（单文件）
├── page[0]: 文件头（版本、页大小）
├── B+Tree: patients 表（主键 id 为键）      → 页 1、5、9 ...
├── B+Tree: diagnoses 表（patient_id 索引）  → 页 3、7 ...
├── B+Tree: labs / medications / events ...
└── 空闲页链（VACUUM 可回收）
```

### 3.2 列存（Columnar，ClickHouse/DuckDB/Parquet）

同一列的值**连续存放**，一页只存一列：

```text
┌──────────┐ ┌──────────────┐ ┌───────────┐
│ name 列   │ │ birth_date 列 │ │ sex 列     │
│ P001-合格│ │ 1970-05-01   │ │ M         │
│ P002-年龄│ │ 1940-01-01   │ │ M         │
│ ...      │ │ ...          │ │ ...       │
└──────────┘ └──────────────┘ └───────────┘
```

适合：**只读大范围扫描 + 聚合**（`SELECT AVG(age) FROM 1000 万患者` 只需读 age 一列）。
代价：**整行读要跨多列拼接**。入组筛查要逐患者下结论（整行语义），列存反而不顺；
但"批量导出统计报表"（入组率、年龄分布）是它的主场。

### 3.3 邻接表（Adjacency list，图库/图算法常用）

每个节点存一份"邻居列表"，遍历 = 沿列表走：

```text
hash: {node -> [(neighbor, relation, chunk_id), ...]}

"星辰科技" -> [("星图平台", "发布方", C3), ("林远", "创始人", C7)]
"星图平台" -> [("星辰智能", "研发方", C4)]
"林远"     -> []
```

适合：**图上任意跳转**——问"创始人"就是查 `星辰科技` 的列表，命中 `林远`。
本仓库 `graph.pkl` 用的 NetworkX DiGraph 就是内存邻接表（dict of dict），
多跳扩展（hop1→hop2）就是两次邻居查找。代价：**全局遍历/跨图聚合弱**（没有索引结构）。

### 3.4 CSR（Compressed Sparse Row，内存图引擎/GraphBLAS/图数据库底层）

三个并行数组压缩存图，**零指针、缓存友好**，是最大规模图的首选：

```text
顶点: [星辰科技, 星图平台, 林远]          (0, 1, 2)
OFFSET  [0, 2, 3, 3]            ← 每个顶点的边在 NEIGHBORS 里的起点
NEIGHBORS [1, 2, 2]             ← 边的终点
EDGE_ATTR ["发布方C3", "创始人C7", "研发方C4"]  ← 边属性并行数组

遍历 星辰科技(0) 的邻居 = NEIGHBORS[OFFSET[0]:OFFSET[1]] = [1, 2] → 星图平台、林远
```

适合：**千万级节点图的内存遍历与 PageRank**（数组连续读，CPU 缓存命中率高）。
代价：**图结构变动要重建三个数组**（静态快照友好，动态增删不友好）。

## 4. 查询语言对比：SQL vs Cypher（同一事实，两种表达）

同一事实："找星辰科技发布过的东西"：

```sql
-- SQL（关系：发布方关系表 relation(head, rel, tail)）
SELECT r.tail FROM relation r
WHERE r.head = '星辰科技' AND r.rel = '发布方';
```

```cypher
-- Cypher（图：节点-边-节点 模式匹配）
MATCH (h:Entity {name: '星辰科技'})-[:发布方]->(t:Entity)
RETURN t.name;
```

**"多跳"才是分水岭**——找 2 跳内所有关联：

```sql
-- SQL：JOIN 自己两次，深度写死在 SQL 里，3 跳要再写一遍
SELECT t2.tail FROM relation r1
JOIN relation r2 ON r2.head = r1.tail
WHERE r1.head = '星辰科技';
```

```cypher
-- Cypher：可变长度路径，深度是参数
MATCH (h:Entity {name: '星辰科技'})-[:*1..2]->(t:Entity)
RETURN DISTINCT t.name;
```

| 能力 | SQL（关系） | Cypher（图） |
|---|---|---|
| 属性过滤 / 聚合 | ★★★ 一等公民（WHERE/GROUP BY 极强） | ★★ 可以但要借助子查询/函数 |
| 不定深多跳遍历 | ★ 要手写 N 次 JOIN（或递归 CTE，仍吃力） | ★★★ 可变路径模式内建 |
| include/exclude 集合语义 | ★★★ EXISTS / NOT EXISTS 天然对应 | ★ 要借 NOT MATCH，反直觉 |
| 缺失值（NULL）三值逻辑 | ★★★ SQL 标准支持 | ★ 图一般无 NULL 边，靠"无此边"表达 |
| 数据完整性约束 | ★★★ 外键/CHECK 声明式 | ★ 大多靠应用层 |

## 5. 关系 vs 图：分维度对比

| 维度 | 关系存储（SQLite/Postgres） | 图存储（NetworkX/Neo4j） |
|---|---|---|
| 逻辑模型 | 表 + 外键（schema 先行） | 节点 + 边（schema-lite，灵活） |
| 查询抽象 | 关系代数（选择/投影/连接/分组） | 路径模式匹配（模式→匹配→投影） |
| 多跳深度 | 差（JOIN 深度写死 / 递归 CTE 有限） | 好（可变长度路径内建） |
| 聚合与统计 | 好（GROUP BY / 窗口函数） | 弱（需 Graph Data Science 库） |
| 缺失/未知语义 | 好（NULL + 三值逻辑 + NOT NULL 约束） | 弱（"没有边"和"未知"难区分） |
| 约束与完整性 | 强（外键 / CHECK / 事务 ACID） | 弱（多数图库无 ACID 外键） |
| 规模扩展 | 成熟（B+Tree、分片、列存扩展） | 内存图快，磁盘图仍在演化 |
| 适合的查询 | 确定性属性筛选、集合判定、报表 | 关系发现、链路解释、推荐路径 |
| 用户心智 | 表、行、条件、集合 | 图、路径、邻居、跳数 |

**关键洞察**：两种模型擅长**不同的问题族**。
入组筛查是"确定性条件 + 集合判定 + 可审计缺失"——关系模型（B 行）；
多跳问答是"关系发现 + 路径解释"——图模型（A 行）。
**没有谁取代谁，只有谁更贴问题**。

## 6. 场景 → 存储选型结论表

| 场景 | 查询形态 | 逻辑模型 | 执行引擎 | 物理存储 | 为什么 |
|---|---|---|---|---|---|
| 知识库多跳问答 | 自然语言 + 关系链 | 属性图 | 图算子 + ANN + PPR | 内存邻接表（pkl）+ FAISS + PPR 缓存 | 问题在"链"，图让跳转 O(1) 邻居查找；向量让语义召回模糊匹配 |
| 科研入组筛查 | 条件 IR → SQL 语义 | 关系（5 表） | SQLite 查询计划器 | 单文件 B+Tree 行存 | 判定在"集合"，EXISTS/NOT EXISTS 天然对应 include/exclude；NULL 三值逻辑内建；可审计、零依赖 |
| （对比）万人入组统计报表 | 聚合查询 | 关系宽表 | 列式引擎 | 列存 / Parquet | 只读大扫描 + 聚合，列存压缩与带宽最优 |
| （对比）千万实体知识图谱分析 | 模式匹配 | 属性图 | 图数据库引擎 | CSR / 邻接表 + 图分片 | 需要最大规模内存遍历与全局算法 |

**统一门面的意义**：入口协议统一（`UnifiedEngine.search`）、结果信封统一（`UnifiedResult`）、
引擎注册表 + 路由统一——但**物理层各用各的格式**。这样：

1. 每个场景拿到**最适合它的存储格式**（图 vs 行存 vs 列存……互不拖累）；
2. 应用侧**只面对一个 API**，路由规则（显式 query_type / 关键词 / 输入形态）决定走哪个引擎；
3. 未来加第三个场景（如文档向量检索、列式报表），只需**注册新引擎**，入口不变。
